## 핵심 내용 요약
- 분산 kv저장소 -> CAP 모두를 만족할순 없다.
    - Consistency: 언제나 같은 데이터 
    - Availability: 일부 노드 장애 생겨도 응답 반환
    - Partition tolerance: 노드간 통신장애가 발생하더라도 시스템은 동작해야한다.
- P는 선택할수 있는 사항이 아니라 무조건 취하고, CP 혹은 AP 시스템을 선택해야한다. 
- CP: 문제 생기면 write 포기. AP: 문제 생겨도 일단 write 진행.
- W + R > N 이어야 강한 일관성이 유지된다.
- 일관성이 깨지는 경우 -> 데이터 버져닝(벡터시계)으로 해결할수 있다. 

- 분산 시스템을 위한 유일 ID 생성 방법 -> uuid(128bit제약), 티켓서버, 스노플레이크 
- 스노 플레이크: 타임스탬프 + 데이터센터/서버 id + 일련번호 조합으로 id 만들기. -> 타임스탬프의 길이 제한에 유의해야함.

- 블룸 필터?
```
Apache Cassandra에서 읽기(Read) 요청이 발생했을 때, 메모리 캐시(Key Cache) 미스가 나면 블룸 필터(Bloom Filter)를 가장 먼저 확인합니다.

이때 블룸 필터의 핵심 목적은 "찾으려는 데이터(Row Key)가 디스크(SSTable)에 '확실히 없는지' 메모리 단에서 초고속으로 걸러내어, 불필요한 디스크 I/O를 최소화하는 것"입니다.

조금 더 구체적인 동작 방식과 이유는 다음과 같습니다.

1. 왜 블룸 필터가 필요한가? (배경)
Cassandra는 쓰기 성능을 극대화하기 위해 데이터를 디스크에 바로 수정하지 않고, 메모리(Memtable)에 모았다가 정기적으로 디스크에 순차적으로 저장(Flush)합니다.

이 때문에 디스크에는 여러 개의 SSTable(Sorted String Table) 파일들이 쌓이게 됩니다.

만약 블룸 필터가 없다면, 특정 데이터를 찾기 위해 디스크에 있는 수많은 SSTable 파일을 하나하나 전부 뒤져야 하는 끔찍한 디스크 읽기 병목(Read Amplification)이 발생합니다.

2. 블룸 필터의 실제 역할
Cassandra는 각 SSTable 파일마다 대응되는 작은 블룸 필터를 메모리(RAM)에 올려두고 관리합니다.

캐시 미스가 나면 디스크로 가기 전, 메모리에 있는 블룸 필터에게 *"이 SSTable에 내가 찾는 키가 있어?"*라고 물어봅니다.

"확실히 없어!" (Negative): 해당 SSTable은 쳐다보지도 않고 패스합니다. (디스크 읽기 패스)

"어? 있는 것 같은데?" (Positive): 이때만 실제 디스크를 열어 해당 SSTable의 인덱스를 확인하고 데이터를 읽어옵니다.

요약하자면
블룸 필터의 목적은 "어차피 데이터가 없는 SSTable 파일 때문에 디스크 읽기(I/O)를 하느라 시스템이 느려지는 걸 방지하는 초고속 방어벽" 역할을 하는 것입니다. 이 덕분에 Cassandra는 디스크 검색 횟수를 획기적으로 줄여 대규모 분산 환경에서도 빠른 읽기 성능을 유지할 수 있습니다
```

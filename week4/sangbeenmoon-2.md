## 핵심 내용 요약

- 다중 마스터 복제 : DB 서버 수(k) 에 비례해서 ID 증가.
- UUID : 128bit 짜리 random 값. 
  - 각 서버에서 독자적으로 ID 생성 가능.
  - 시간순 정렬 불가. numeric (X)
- 티켓 서버 : 중앙 집중 DB 서버를 한대 두고 auto_increment 활용.
  - 티켓서버가 SPOF
- 트위터 스노플레이크 : sign bit(1) / timestamp(41) / datacenter ID(5) / server ID (5) / 일련번호(12)

## 의문이 드는 내용 / 동의하지 않는 내용
> 책의 주장에 대한 비판적인 관점
#### 트위터 스노플레이크 접근법의 한계
- 시계 의존성과 시계 역행(clock skew) 문제 : NTP 동기화, 윤초, VM 마이그레이션 등으로 시계가 뒤로 돌아가면 이미 발급한 것보다 작은 타임스탬프가 생기고, 이때 ID 중복 위험이 생깁니다.
- 수명 한계 (약 69년)
- 머신 ID 할당·조정의 운영 부담 : 10비트라 최대 1024대까지만 고유 노드를 둘 수 있고, 어떤 두 노드도 같은 머신 ID를 갖지 않도록 반드시 조정해야 합니다. 정적 환경이라면 설정으로 해결되지만, 쿠버네티스·오토스케일링처럼 노드가 수시로 뜨고 죽는 동적 환경에서는 안정적인 고유 ID를 부여하기가 까다로워 ZooKeeper/etcd 같은 별도 코디네이션이 필요해집니다.
- 밀리초당 발급량 상한 : 시퀀스가 12비트라 한 노드가 1밀리초에 4096개까지만 만들 수 있습니다(초당 약 400만 개). 그 이상 폭주하면 다음 밀리초까지 블로킹해야 합니다. 보통은 충분하지만 하드 캡이 존재한다는 점은 유의해야 합니다.
- 정보 노출(information leakage) : ID에 타임스탬프가 그대로 박혀 있어 생성 시각을 알 수 있고, 시퀀스 증가를 관찰하면 처리량이나 특정 기간의 데이터 생성량(가입 수 등)을 추정할 수 있습니다. 순차적이라 열거(enumeration)에도 상대적으로 취약합니다. 비즈니스 지표가 새어나갈 수 있다는 뜻입니다.

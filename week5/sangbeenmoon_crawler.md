161p 서버사이드 렌더링 vs 동적 렌더링
크롤러가 직접 JS를 실행해서 페이지를 완성시키는 위 기법은 보통 동적 렌더링(dynamic rendering) 이라고 불러 (Alex Xu의 『가상 면접 사례로 배우는 대규모 시스템 설계 기초』 웹 크롤러 장에서도 이 용어를 써). "렌더링하는 주체"가 크롤러 쪽이야.
반면 진짜 서버측 렌더링(SSR) 은 웹사이트를 만드는 쪽이 쓰는 아키텍처야. Next.js, Nuxt.js처럼 서버가 애초에 완성된 HTML을 만들어서 내려주는 방식이지. 만약 대상 사이트가 SSR로 만들어졌다면, 크롤러가 처음 받는 HTML에 이미 링크가 다 들어있어서 애초에 이 문제가 안 생겨.


156p 미수집 URL 저장소를 위한 지속성 저장장치
대부분의 url 은 디스크에 두지만 IO 비용을 줄이기 위해 메모리버퍼에 큐를 두는 것이다. 버퍼에 있는 데이터는 주기적으로 디스크에 기록할 것이다.

버퍼는 두 개라고 보시면 이해가 쉽습니다.
Enqueue 버퍼 (넣는 쪽 = write 방향)
새로 발견한 URL을 곧바로 디스크에 쓰지 않고, 일단 메모리 버퍼에 모아둡니다. 버퍼가 어느 정도 차면 그때 한 번에(batch) 디스크로 flush 합니다. 매번 쓰는 대신 모아서 한 번에 쓰니까 디스크 쓰기 횟수가 확 줄죠. → 여기가 질문하신 부분이 맞습니다.
Dequeue 버퍼 (꺼내는 쪽 = read 방향)
워커(크롤러 스레드)가 URL을 하나씩 디스크에서 꺼내는 게 아니라, 디스크에서 한 뭉텅이를 미리 메모리 버퍼로 읽어옵니다. 워커들은 이 메모리 버퍼에서 URL을 가져가고, 버퍼가 비면 다시 디스크에서 뭉텅이로 채웁니다.

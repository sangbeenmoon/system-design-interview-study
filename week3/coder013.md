### 처리율 제한 장치(rate limiter)

- Dos(Denial of Service) 공격에 의한 자원 고갈(resource starvation)을 방지할 수 있다. (p51)
- 호출하는 API에 대한 과금이 횟수에 따라 이루어진다면, 그 횟수를 제한할 수 있어야 비용을 절감할 수 있을 것이다. (p52)
- 서버 과부하를 막는다. (p52)
- 보통 API 게이트웨이(gateway)라 불리는 컴포넌트에 구현된다. (p55)
- 그렇다면 이 카운터는 어디 보관할 것인가? 데이터베이스는 디스크 접근 때문에 느리니까 사용하면 안 될 것이다. 메모리상에서 동작하는 캐시가 바람직한데, 빠른데다 시간에 기반한 만료 정책을 지원하기 때문이다. (p66)
- 어떤 요청이 한도 제한에 걸리면 API는 HTTP 429 응답(too many requests)을 클라이언트에게 보낸다. (p68)

- 정렬 집합(sorted set)

### 처리율 제한 알고리즘

#### 토큰 버킷(token bucket)

- 지정된 용량의 버킷이 있으며, 주기적으로 토큰이 채워진다.
- 토큰이 없는 경우, 요청을 버린다.
- **버킷 크기**
- **토큰 공급률**: 초당 공급되는 토큰 개수

#### 누출 버킷(leaky bucket)

- 지정된 용량의 큐가 있으며, 요청을 받으면 큐에 넣는다.
- 지정된 시간마다 큐에서 요청을 꺼내 처리하며, 큐가 꽉차있는 경우 요청을 버린다.
- 일반적으로 FIFO(First-In-First-Out) 구조
- 단시간에 트래픽이 몰리는 경우 오래된 요청을 빠르게 처리하지 못한다면 최신 요청들이 버려진다.
- **버킷 크기**
- **처리율(outflow rate)**: 지정된 시간당 처리할 요청 수

#### 고정 윈도 카운터(fixed window counter)

- 타임라인(timeline)을 고정된 간격의 윈도(window)로 나누고, 각 윈도마다 카운터(counter)를 붙인다.
- = 시간을 고정된 간격으로 나누고, 각 시간마다 요청 횟수를 카운트한다.
- 임계치(threshold)에 도달하면 요청을 버린다.
- 시간 경계 부분(00:00:50~00:01:10)에 트래픽이 몰리는 경우 기대했던 임계치보다 많은 양의 요청을 처리하게 된다.

#### 이동 윈도 로그(sliding window log)

- 요청의 타임스탬프(timestamp)를 추적한다.
- 새 요청의 타임스탬프를 로그(log)에 추가하고, 로그의 크기가 허용치보다 크다면 해당 요청을 무시한다.
- 새 요청이 올 때마다 만료된 타임스탬프는 제거된다.
- 만료 기준은 윈도 시작 시간 이전이며, 새 요청의 타임스탬프를 윈도 종료 시간으로 본다.
- 거부한 요청의 타임스탬프도 모두 저장하기 때문에 다량의 메모리를 사용한다.

#### 이동 윈도 카운터(sliding window counter)

- 고정 윈도 카운터와 이동 윈도 로그를 결합한 방식
- **임계치 계산식**: 현재 1분간의 요청 수 + 직전 1분간의 요청 수 \* 이동 윈도와 직전 1분이 겹치는 비율
